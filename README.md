# nuxnet-inference

`nuxnet-inference` is a CLI-focused 3D nuclei localization and segmentation inference package for volumetric microscopy images, built around a 3D U-Net backbone [2,3].
It is designed for high-throughput usage where nuclei are segmented as foreground instances and can be converted into centroid-level measurements for downstream quantification.

Scientifically, this project follows the NuMorph setting for whole-brain nuclei analysis in cleared tissue and light-sheet microscopy volumes [1].
Operationally, it is intended to plug into Nextflow workflows (nf-core style), in particular the `nf-core/lsmquant` pipeline context.

For reproducibility, the runtime follows the same technical direction used in the mlf-core framework [4,5]: explicit random-seed control plus an optional deterministic execution mode for PyTorch/CUDA (`--deterministic`) where backend support allows.
This makes repeatable inference behavior easier to enforce in automated pipeline execution.

From a model-family perspective, this repository currently provides U-Net-based segmentation for volumetric inference; modern convolutional backbones such as ConvNeXt [6] are relevant architectural context for future model evolution but are not the default architecture in this package.

**This repository reproduces the training pipeline at inference time.** A checkpoint from
[`nuxnet-training`](https://github.com/luiskuhn/nuxnet-training) is only meaningful if
inference feeds it what the trainer fed it. The CLI therefore resamples to the training
voxel grid, tiles to the training patch size, and projects the result back onto the grid
of the file you passed in. On the bundled example the same weights score **0.456** with
whole-volume inference at the stored sampling and **0.739** with training-grid inference —
the difference is the pipeline, not the model. On the full 32-volume validation set the
training-grid path scores 0.801 on the grid the network was trained for.

This repository ships:

- an inference CLI: `nuxnet-pred`
- the **trainer's own** 3D U-Net, vendored verbatim so checkpoints load with `strict=True`
- the **trainer's own** dataloading and resampling, vendored verbatim
- training-grid inference: resample → normalize → tile → forward → blend → threshold → project back
- OME-TIFF I/O carrying physical calibration, and optional nuclei post-processing (TSV)
- a bundled real image/mask pair plus a scoring script, so a run has a number attached
- a BioImage.IO package builder and verifier (`scripts/`)

## Install

### Python version support

This project is tested to run on Python 3.9 through 3.12.
For the best compatibility with current dependencies, we recommend Python 3.12.

```console
pip install .
```

For development and the reporting/packaging scripts:

```console
pip install -r requirements.txt
```

Inference needs PyTorch. A CUDA build is strongly preferred: the 32-volume validation
below took ~4 minutes per volume on a Tesla T4 and considerably longer on CPU.

Verify the install:

```console
nuxnet-pred --help
```

## Quick start

Run with autogenerated dummy 3D input and random UNet3D weights:

```console
nuxnet-pred smoke-test --arch unet3d --output ./predictions/demo
```

Run deterministic smoke-test (mlf-core style runtime controls):

```console
nuxnet-pred smoke-test --arch unet3d --output ./predictions/demo_det --deterministic
```

Run with a custom OME-TIFF 3D input volume (with `ZYX` axes):

```console
nuxnet-pred predict --arch unet3d --input ./input_volume.ome.tiff --output ./predictions/demo
```

**Run the way the packaged checkpoint expects** — this is the configuration that produced
every number in this README:

```console
nuxnet-pred predict \
    --input  ./volume.ome.tif \
    --model  ./numorph_fold1_weights.pt \
    --output ./predictions/volume \
    --classes 2 --in-channels 1 --dropout-rate 0.1 \
    --target-voxel-spacing 3.0,1.0,1.0 \
    --patch-size 32,128,128 \
    --overlap 0.5 \
    --threshold 0.8 \
    --postprocess-instances
```

Run deterministic inference:

```console
nuxnet-pred predict --arch unet3d --input ./input_volume.ome.tiff --output ./predictions/demo_det --deterministic
```

Run inference and extract nuclei instances table (TSV):

```console
nuxnet-pred predict --arch unet3d --input ./input_volume.ome.tiff --output ./predictions/demo --postprocess-instances --nuclei-label 1 --neighbor-radius 2.0
```

Disable normalization if needed:

```console
nuxnet-pred predict --arch unet3d --input ./input_volume.ome.tiff --output ./predictions/demo --no-normalize-input
```

Run with a checkpoint:

```console
nuxnet-pred predict --arch unet3d --classes 3 --in-channels 1 --model ./checkpoint.pt --input ./input_volume.ome.tiff --output ./predictions/demo
```

## Run it on the bundled example, and score it

`examples/numorph_c075_0007/` contains one real NuMorph image/ground-truth mask pair,
so the tool can be tested and **scored** without downloading the training dataset. The
volume is stored at 2.5 / 0.75 / 0.75 µm, deliberately not on the network's
3.0 / 1.0 / 1.0 µm grid, so a run exercises resampling, tiling and projection back.

```console
nuxnet-pred predict \
    --input  examples/numorph_c075_0007/c075_0007_Bottom3.image.ome.tif \
    --model  /path/to/numorph_fold1_weights.pt \
    --output runs/c075 \
    --classes 2 --dropout-rate 0.1 \
    --target-voxel-spacing 3.0,1.0,1.0 \
    --patch-size 32,128,128 \
    --threshold 0.8 \
    --postprocess-instances

python scripts/score_example.py \
    --prediction runs/c075.ome.tiff \
    --truth      examples/numorph_c075_0007/c075_0007_Bottom3.mask.ome.tif
```

Expected with `numorph_fold1_weights.pt`:

```
source voxel size   [2.5, 0.75, 0.75] um
target voxel size   [3.0, 1.0, 1.0] um
resampled           True

training-grid Dice  0.8601   <- network, from the written mask
round-trip ceiling  0.7877   <- a PERFECT mask after the same round trip
input-grid Dice     0.7390   <- what was written to disk
fraction of ceiling 93.8%
```

The ceiling matters: 64 slices compress to 53 on the training grid and back, which
alone caps a perfect mask at 0.788 on this volume. Reading 0.739 as "74% correct"
understates it — it is 94% of what the round trip allows. If your number lands well
below the ceiling, the model is losing something. If it lands near it, the remaining gap
is the export.

See `examples/numorph_c075_0007/README.md` for the measurements, the source filenames,
the sha256s, and the dataset's pending licence status.

## What the model is, and is not

The target is **not** a filled nucleus body, and it is **not** a one-voxel point.

NuMorph masks are **2D single-slice discs** marking the middle Z of each nucleus, stored
in a 3D volume. Measured on the bundled example pair:

| property | value |
|---|---|
| components | 684 single-slice discs (680 under 26-connectivity) |
| component size | median 63 voxels, range 1–134 |
| component Z-thickness | 1 slice, 100% |
| XY extent | ~14 px (≈14 µm in XY, ≈3 µm in Z) |
| foreground | 1.32% of voxels |

Consequences, stated plainly:

- **A predicted component of 1–2 voxels is badly under-segmenting**, not merely sparse.
  Component size is a genuine diagnostic, not decoration.
- **This is a detection target.** Expect one slice per object even when the nucleus
  spans several. If you need filled nuclei, this model gives you detections to seed a
  watershed; its foreground is not a segmentation of nucleus volume.
- **Dice on this dataset measures agreement on flat disc markers.** It is not comparable
  with a 3D segmentation score.

## Preparing your own input

The CLI reads **OME-TIFF** (`.ome.tif` / `.ome.tiff`) and takes the physical voxel size
from the OME-XML. Two requirements and one recommendation:

| | requirement | what happens if not met |
|---|---|---|
| axes | series must contain `ZYX` | rejected: `Expected OME-TIFF axes to include ZYX, got axes 'QYX'` |
| calibration | `PhysicalSizeZ/Y/X` in the OME-XML | runs, but prints a warning and uses the stored sampling |
| channels | one channel; extra singleton axes are squeezed | non-singleton extras are rejected |

A **plain TIFF is rejected**, even though the pipeline has a no-metadata path — the file
must at least declare `ZYX` axes. To convert:

```python
import tifffile

volume = tifffile.imread("plain.tif")          # must already be ZYX
tifffile.imwrite(
    "converted.ome.tif", volume, ome=True,
    metadata={"axes": "ZYX",
              "PhysicalSizeZ": 5.0, "PhysicalSizeY": 3.545, "PhysicalSizeX": 3.545,
              "PhysicalSizeZUnit": "µm", "PhysicalSizeYUnit": "µm", "PhysicalSizeXUnit": "µm"},
)
```

**Running without calibration is allowed but not trustworthy.** The CLI warns:

```
warning: input carries no PhysicalSize metadata; voxel spacing is unknown, so
the volume is used at its stored sampling. A checkpoint trained with resampling
will be out of distribution here.
```

Get the calibration into the file before you judge the output.

### From OME-Zarr

OME-Zarr holds the same information but the CLI does not read it. Extract the channel you
want — a nuclear stain such as DAPI or SYTOX is the appropriate contrast — along with the
scale from the multiscales metadata, and write an OME-TIFF:

```python
import zarr, tifffile

store = "dataset.zarr"
group = zarr.open_group(store, mode="r")        # works with zarr 2.x and 3.x for a local path
meta  = group["0"].attrs["multiscales"][0]
scale = meta["datasets"][0]["coordinateTransformations"][0]["scale"]
names = [axis["name"] for axis in meta["axes"]]
# `scale` is ordered like `names`, e.g. names=[t,c,z,y,x] -> scale=[1,1,5.0,3.55,3.55]

channel = 0                                     # whichever channel is the nuclear stain
z0, z1 = 0, 256                                 # read a crop; the full channel may not fit in RAM
volume = group["0"]["0"][0, channel, z0:z1]     # -> (z, y, x) uint16

spacing = {name: scale[names.index(name)] for name in ("z", "y", "x")}
tifffile.imwrite(
    "nuclei_channel.ome.tif", volume, ome=True,
    metadata={"axes": "ZYX",
              "PhysicalSizeZ": spacing["z"],
              "PhysicalSizeY": spacing["y"],
              "PhysicalSizeX": spacing["x"],
              "PhysicalSizeZUnit": "µm", "PhysicalSizeYUnit": "µm", "PhysicalSizeXUnit": "µm"},
)
```

Indexing the scale by **axis name** rather than by position matters: the order depends on
what the writer declared, and `scale[-3:]` is only `ZYX` when the axes happen to be
`...ZYX`. For the `ear1_1-6m` dataset above, `names` is `[t, c, z, y, x]` and the spacing
comes out as `5.005 / 3.545 / 3.545` µm.

Read a crop rather than the whole channel — a 1353×3162×2422 `uint16` channel is ~20 GB,
and the CLI tiles internally anyway, so a few hundred slices is enough to judge a run.

Note that data acquired at a different voxel size than the training range
(2.5–4.0 µm Z, 0.75–1.21 µm XY) will be resampled hard, and XY detail that was never
acquired cannot be invented. Expect degraded but not meaningless output, and score it
against something before trusting it.

### Running directly on OME-Zarr, and writing the mask back into the store

Extracting a TIFF is fine for one crop. For a real volume — or any case where you want the
mask to sit on the image in a viewer — `scripts/predict_zarr_chunks.py` reads the store
directly and writes the result as a **sibling group of the image series**, so napari opens
both layers with no manual alignment.

```bash
python scripts/predict_zarr_chunks.py \
    --zarr /data/ear1_1-6m.lite.zarr \
    --channel 0 \
    --model models/fold1.pt \
    --layer-name nuclei_mask \
    --z-range 48:264 --y-range 1480:2170 --x-range 400:1030 \
    --chunk 216,690,630 --halo 0,0,0 \
    --overlap 0.25 --levels 3
```

Three details in that command are load-bearing:

**`--cuda` is opt-in.** The CLI declares `--cuda/--no-cuda` with `default=False`, so a run
without the flag silently executes on CPU. Measured on one chunk of this ear: 425 s on CPU
against 49.7 s on a T4, with identical foreground (1.293%). The chunker passes `--cuda`
explicitly unless you give `--cpu`.

**Normalization is shared, not per chunk.** The CLI's default is one min/max per volume,
which is what training did. Applied to each chunk independently, identical tissue gets
different contrast depending on where it landed. Measured: splitting a region and
normalizing each part separately changed ~1% of voxels and dropped Dice between tiled and
untiled results to **0.458**. The chunker therefore derives one range for the whole region
and passes it to every chunk via `--normalization-range`.

**`--halo` is context, not overlap.** `--overlap` is the CLI's internal sliding-window
overlap *inside* one chunk. `--halo` grows each chunk outward so the network sees a full
receptive field near the chunk boundary; the halo is computed and then discarded. The
network's receptive field is 60 voxels on the training grid, so half of it is 90 µm in Z —
18 source voxels at this spacing. The default is derived from that arithmetic rather than
hand-picked, because an 8-voxel Z halo covers only 40 µm and clips nuclei near boundaries.
Leaving the default out prints what it chose.

If a single region fits in memory, do not chunk at all: `--chunk` equal to the region and
`--halo 0,0,0` processes it as one volume, which makes per-volume normalization exactly
training-equivalent and leaves no seams to reason about. That is what the command above
does — 216×690×630 resamples to 360×2446×2234, 7.87 GB, which fits.

Output is a root-level group beside the image series:

```
ear1_1-6m.lite.zarr/
  0/                    image series, [t, c, z, y, x]
  nuclei_mask/          [z, y, x] uint8, binary, multiscale
```

with `scale` and `translation` taken per axis by name from the image's multiscales entry,
so `physical = index * scale + translation` holds for the mask exactly as for the image.
Lower pyramid levels are **max**-pooled: averaging a sparse binary layer fades nuclei
below any threshold when you zoom out, which reads as missing detections.

To inspect it, with `[z, y, x]` layers already sharing a physical frame:

```bash
napari /data/ear1_1-6m.lite.zarr
```

If you would rather have a small, self-contained scene — for example to copy to a laptop —
`scripts/export_roi_scene.py` writes one with the image, the mask and (optionally) the
detections, all in absolute specimen coordinates:

```bash
python scripts/export_roi_scene.py \
    --zarr /data/ear1_1-6m.lite.zarr --layer nuclei_mask \
    --out ear1_1-6m_roi.zarr --spots roi_crop.spots.npz \
    --z-range 48:264 --y-range 1480:2170 --x-range 400:1030
```

```bash
napari ear1_1-6m_roi.zarr
```

## Output format

For an input `volume.ome.tif` and `--output out/volume`:

| file | contents |
|---|---|
| `out/volume.ome.tiff` | binary mask, `uint8`, values `{0, 1}`, `ZYX`, **on the input grid**, carrying the input's `PhysicalSize` |
| `out/volume.nuclei.tsv` | one row per detected object (only with `--postprocess-instances`) |

The mask is `uint8` with exactly two unique values, shape equal to the input volume, and
the same physical calibration as the input — resampling preserves physical extent, so both
grids describe the same specimen.

TSV columns:

```
id	z	y	x	size_voxels
1	0.000	7.375	93.531	96
2	0.000	12.041	113.438	73
```

`z, y, x` are centroids in **voxel** units of the input grid; `size_voxels` is the number
of voxels in the recovered component. One row per object, `id` starting at 1.

### Folder mode

Pass a directory and the tree is mirrored into the output directory:

```console
nuxnet-pred predict --input ./volumes/ --output ./predictions/ --model ./fold1.pt ...
```

```
volumes/            predictions/
  a.ome.tif    ->     a.ome.tiff
                      a.nuclei.tsv
  sub/b.ome.tif ->    sub/b.ome.tiff
```

Which files are picked up, in order, deduplicated and sorted:
`*.ome.tiff`, `*.ome.tif`, `*.tiff`, `*.tif`.

## CLI overview

The `nuxnet-pred` CLI exposes two explicit subcommands:

- `predict`: run inference from one OME-TIFF volume or from all TIFF/OME-TIFF files in a folder.
- `smoke-test`: generate a random 3D volume, initialize an untrained model, run a forward pass, and write the predicted mask.

Both commands save masks as OME-TIFF files (`.ome.tiff`) with `ZYX` axes metadata. When `--postprocess-instances` is enabled in `predict`, a nuclei table is also written as `<output>.nuclei.tsv`.

`predict` has two modes, selected by whether you pass `--target-voxel-spacing` or
`--patch-size`:

| mode | activated by | behaviour |
|---|---|---|
| **training-grid** (recommended) | `--target-voxel-spacing` and/or `--patch-size` | resample → normalize → tile → blend → threshold → project back |
| **whole-volume** (legacy) | neither flag | one forward pass over the whole volume at its stored sampling |

The legacy path prints a warning, because a checkpoint trained with resampling will be out
of distribution on it.

## CLI parameters

Shared model/runtime parameters (available in both commands):

- `--arch [unet3d|dummy]`: model architecture.
- `--classes INTEGER`: number of output channels including background. The NuMorph nucleus-marker task uses `2`. Default `2`.
- `--in-channels INTEGER`: number of input channels expected by the model. Default `1`.
- `--dropout-rate FLOAT`: dropout used in UNet3D blocks; must match the trained checkpoint. Default `0.1`.
- `--seed INTEGER`: seed used for reproducibility. Default `42`.
- `--cuda/--no-cuda`: enable CUDA when available.
- `--deterministic/--no-deterministic`: toggle mlf-core-style deterministic runtime settings (CuDNN/CuBLAS/PyTorch deterministic algorithms). Default `no-deterministic`.
- `--normalize-input/--no-normalize-input`: enable/disable min/max intensity normalization. Default `normalize-input`. Leave enabled for the NuMorph checkpoint: it was trained with `normalize_input: true`.

`predict` parameters:

- `--input TEXT`: input OME-TIFF file or a directory of them. If omitted, random input is generated.
- `--model TEXT`: optional `.pt` checkpoint (plain `state_dict` or a dict containing `state_dict`). If omitted, the model is randomly initialized — useful for smoke tests only.
- `--output TEXT`: output prefix (single input) or output directory (input folder). **Required.**
- `--input-shape TEXT`: shape `D,H,W` used only when `--input` is omitted. Default `16,64,64`.
- `--target-voxel-spacing TEXT`: resample to this `Z,Y,X` spacing in µm before inference, matching the trainer's `--target-voxel-spacing`. Use `3.0,1.0,1.0` for the NuMorph checkpoint.
- `--patch-size TEXT`: sliding-window tile size as `Z,Y,X`. Use `32,128,128` to match the trainer's field of view.
- `--overlap FLOAT`: fraction shared by neighbouring tiles. Default `0.5`.
- `--threshold FLOAT`: foreground probability threshold; only used with `--patch-size`. Default `0.5`; the trained checkpoint was validated at `0.8`.
- `--postprocess-instances/--no-postprocess-instances`: enable/disable nuclei instance extraction and TSV export. Default off.
- `--nuclei-label INTEGER`: class label interpreted as nuclei in the predicted mask. Default `1`.
- `--neighbor-radius FLOAT`: radius used by KDTree to build the voxel-neighborhood graph. Default `2.0`.

`smoke-test` parameters:

- `--output TEXT`: output prefix for the generated mask.
- `--input-shape TEXT`: random input shape `D,H,W`.

## Training-grid inference in detail

The stage order is not incidental; each step exists because the trainer did it that way.

1. **Read.** One OME-TIFF. Physical voxel size is parsed from the OME-XML in `Z, Y, X`
   order. A file without calibration is reported, not guessed.
2. **Resample.** The trainer's `resample_volume_pair`, vendored verbatim at a mirrored
   path, resamples to `3.0 / 1.0 / 1.0` µm while preserving physical extent. Gaussian
   anti-aliasing when downsampling; nearest-neighbour is reserved for labels.
3. **Normalize.** Per-volume min-max to `[0, 1]`, applied **after** resampling — the same
   order as the trainer.
4. **Tile.** Sliding window `32 × 128 × 128` at 50% overlap. Each tile is padded so every
   spatial axis is a multiple of 4: the decoder upsamples twice, and an axis like 53
   otherwise raises a tensor-size mismatch inside `torch.cat`.
5. **Forward.** Two-channel output `[background, marker]`; `softmax(dim=1)` gives the
   marker probability. The packaged weights emit **logits**, not probabilities.
6. **Blend.** Overlapping tiles combined with a separable Hann taper. Voxels are divided
   only where a window actually contributed — clamping the denominator instead rescaled
   corner voxels from 0.90 down to 0.04.
7. **Threshold.** `0.80` on the training grid, where the checkpoint was calibrated.
8. **Project back.** The binary mask is interpolated **trilinearly** to the input grid and
   re-thresholded at `0.5`. Nearest-neighbour duplicated one slice in six and capped a
   *perfect* mask at Dice 0.50; trilinear on the mask reached 0.85 of ceiling.
9. **Write.** OME-TIFF mask on the input grid, binary `0/1`, carrying `PhysicalSize`, plus
   the nuclei TSV.

Measured comparison of the projection rule on two volumes:

| volume | ceiling | nearest | trilinear mask | probability-then-threshold |
|---|---|---|---|---|
| C075_0007 | 0.788 | 0.454 | **0.739** | 0.452 |
| C121_0009 | 0.983 | 0.390 | **0.800** | 0.658 |

Threshold sensitivity across all 32 validation volumes: Dice is flat from `0.4` to `0.9`
(spread 0.008, from 0.7925 at 0.40 to 0.8006 at 0.80). The operating point is therefore
not tuned to the test data.

## Post-processing for nuclei localization (TSV export)

To execute post-processing, run `predict` with `--postprocess-instances`:

```console
nuxnet-pred predict --arch unet3d --input ./input_volume.ome.tiff --output ./predictions/demo --postprocess-instances --nuclei-label 1 --neighbor-radius 2.0
```

This writes:

- segmentation mask: `./predictions/demo.ome.tiff`
- nuclei table: `./predictions/demo.nuclei.tsv`

This code is **unchanged** from the original implementation. It runs on the mask as
written, whichever mode produced it.

Algorithm summary (current implementation):

1. Build nuclei mask from predicted class label (`--nuclei-label`).
2. Extract nuclei voxel coordinates from the binary mask.
3. Build a SciPy KDTree and run radius range queries (`scipy.spatial.KDTree`, `query_ball_point`) to find nearby nuclei voxels.
4. Build a voxel topology graph in NetworkX (`networkx.DiGraph`) from neighbor relations.
5. Extract clusters using strongly connected components (`networkx.strongly_connected_components`).
6. Compute centroid `(z, y, x)` and `size_voxels` per component and export TSV.

Python libraries/functions used:

- Scikit-Image: `skimage.exposure.rescale_intensity` (optional input normalization), `skimage.measure.label` (mask labeling helper).
- SciPy: `scipy.spatial.KDTree`, `KDTree.query_ball_point`.
- NetworkX: `networkx.DiGraph`, `networkx.strongly_connected_components`.

Because the graph is built over every foreground voxel, cost grows with foreground volume.
On a 64×224×224 volume (~1% foreground) it is seconds; on a large stitched volume it is
minutes. Run it on the volumes you need rather than the whole brain at once.

## Validation on the NuMorph training dataset

32 training volumes (two acquisition groups, five-fold cross-validation data), fold-1
checkpoint, Tesla T4, `--threshold 0.8`.

| metric | mean | min | max |
|---|---|---|---|
| train-grid Dice | **0.801** | 0.681 | 0.876 |
| round-trip ceiling | 0.883 | 0.761 | 0.988 |
| input-grid Dice | **0.749** | 0.587 | 0.846 |
| fraction of ceiling | **85.2%** | | |

Split by group, because they fail in opposite directions:

| group | n | source Z | train | input | ceiling | effect of the round trip |
|---|---|---|---|---|---|---|
| C075 | 16 | 2.5 µm | 0.818 | 0.697 | 0.782 | 64 → 53 slices, **compresses**, loses accuracy |
| C121 | 16 | 4.0 µm | 0.783 | 0.801 | 0.985 | 64 → 85 slices, **upsamples**, gains it |

For C121 the input-grid score is *higher* than the train-grid score — not because the
model improves but because upsampling fills gaps in a way that happens to agree with the
ground truth. Pooling the two groups mixes two different upper bounds, which is why the
split is reported alongside the pooled mean.

68,602 nuclei rows in total across the 32 volumes (median 2,274 per volume).

### Detection accuracy, which Dice understates badly

Dice asks whether the voxels agree. A user asking the tool for nuclei asks a different
question: did you find the nucleus, and where is it? On a marker-style target those come
apart, so they are measured separately by `scripts/detect_metrics.py`, which scores the
centroids produced by the CLI's own unchanged post-processing.

Matching is greedy nearest-neighbour in physical microns at a 7.4 µm tolerance — half the
measured 14.8 µm nucleus diameter. Greedy rather than optimal assignment because it cannot
reshuffle pairs to raise its own score.

| metric | mean | min | max |
|---|---|---|---|
| detection precision | **0.966** | 0.913 | 0.989 |
| detection recall | **0.893** | 0.804 | 0.980 |
| detection F1 | **0.926** | 0.860 | 0.979 |

Median matched-centroid distance is **0.45 µm** — under a sixth of an XY voxel — pooled over
63,467 matched pairs.

Every one of the 32 volumes scores higher on detection F1 than on voxel Dice, which is the
point: the model is a much better detector than its Dice suggests, because a one-voxel edge
difference costs Dice far more than it costs a centroid. If the task is "find and locate the
nuclei", F1 is the number to quote; if it is "reproduce this mask voxel for voxel", Dice is.

```console
python scripts/detect_metrics.py --artifacts /path/to/eval-output --out detection.json
```

### A real volume with no ground truth

NuMorph labels are the model's own training targets, so the figures above are a ceiling of
sorts. The whole-mount ear is the opposite case: no ground-truth mask, and a second opinion
from a different detector.

Region: 216 × 690 × 630 source voxels at 5.005 / 3.5455 / 3.5454 µm, 36% tissue, processed
as one volume in 28.4 min on a T4. Output 64,959 nuclei over 285,352 foreground voxels —
4.4 voxels each, matching the 5-voxel plus-disc target.

Imaris "Spots - Nuclei" reports 39,510 spots in the same region. Comparing against it:

| metric | value |
|---|---|
| model components | 69,917 |
| Dice on rendered marker discs | 0.163 |
| precision vs Imaris | 0.376 |
| recall vs Imaris | 0.665 |
| median matched distance | 4.11 µm |

That precision figure is **not** an accuracy measure and should not be quoted as one. Imaris
is a detector with its own parameters, not ground truth, so the number counts disagreement
between two algorithms. `scripts/check_ear_detections.py` resolves which kind of
disagreement it is, by measuring the SYTOX intensity under each predicted centroid:

| group | n | median intensity (5³ cube) |
|---|---|---|
| tissue floor (signal, no mask) | 65,711 | 1,378 |
| random points on bright signal | 43,189 | 1,905 |
| unmatched components | 43,189 | **2,191** |
| matched components | 26,728 | **2,262** |

Unmatched components carry **0.97×** the intensity of matched ones — statistically
indistinguishable — while sitting at 1.59× the tissue floor and 1.15× the random baseline.
Assignment multiplicity is 1.02 components per matched spot (max 2), so this is not
over-segmentation either.

The model and Imaris disagree about *which nuclei exist*, not about *where a given nucleus
is*: where they agree, the median matched distance is 4.11 µm, under one XY voxel and well
inside a nucleus. Reporting 0.376 as precision would understate the tool; omitting the
comparison would hide a genuine disagreement. Both are reported.

```console
python scripts/compare_ear_spots.py --prediction ear1_1-6m.lite.zarr --layer nuclei_mask_roi \
    --spots roi_crop.spots.npz --z-range 48:264 --y-range 1480:2170 --x-range 400:1030
python scripts/check_ear_detections.py --zarr ear1_1-6m.lite.zarr --layer nuclei_mask_roi \
    --spots roi_crop.spots.npz --z-range 48:264 --y-range 1480:2170 --x-range 400:1030
```

A matplotlib validation report with per-volume slice montages, per-slice Dice curves,
threshold sweeps, the detection page and the ear pages is produced by
`scripts/make_report.py`:

```console
python scripts/make_report.py --artifacts /path/to/eval-output --out report.pdf --limit 6 \
    --detections detection.json \
    --ear-scene ear1_1-6m_roi.zarr \
    --ear-check ear_check.json --ear-compare ear_compare.json
```

The artifacts it expects are the `.prepared.npy`, `.truth_grid.npy`, `.prob.npy` files
written by `scripts/eval_numorph.py`, plus its `summary.json`. The ear pages are optional
and are skipped when their arguments are omitted.

## Checkpoint compatibility and architecture parity

The inference `UNet3D` used to be a hand-written lookalike of the trainer's and could never
load a `nuxnet-training` checkpoint:

| symptom | count |
|---|---|
| trained tensors with no home | 16 |
| tensors the checkpoint does not contain | 34 |
| `shortcut.*` tensors unaccounted for | 30 |

Three separate causes: no residual shortcuts, different module names
(`inc.conv_1` vs `inc.conv_block_1.conv_1`), and `bias=True` on convolutions followed by
BatchNorm where the trainer uses `bias=False`.

The fix is not a rename — it is to **remove the second implementation**. The trainer's file
now lives at a path that mirrors the training package:

```
nuxnet-training     numorph_nuclei_segmentation/model/unet_3d_models.py
nuxnet-inference    nuxnet_inference_package/model/unet_3d_models.py     (verbatim)
nuxnet-training     numorph_nuclei_segmentation/data_loading/data_loader.py
nuxnet-inference    nuxnet_inference_package/data_loading/data_loader.py (verbatim, _ rename documented)
```

`nuxnet_inference_package/models/unet3d.py` remains as a compatibility re-export so
existing imports keep working. New code should import from `nuxnet_inference_package.model`.

All five fold checkpoints load with `strict=True`, 108/108 tensors.

Two tests keep this honest:

- **verbatim check** — with `NUXNET_TRAINING_DIR` pointing at a training checkout, the
  mirrored files must be byte-identical to the trainer's.
- **golden checkpoint check** — without a checkout, 108 parameter names and shapes plus
  the 30 shortcut tensors must match `tests/unet3d_keys.json`, so the regression cannot
  return silently.

```console
NUXNET_TRAINING_DIR=/path/to/nuxnet-training pytest tests/ -q
```

## BioImage.IO packaging

`scripts/build_bioimageio_package.py` builds a spec-`0.5.12` package that reloads
standalone: `rdf.yaml`, `weights.pt`, `unet_3d_models.py`, `environment.yml`, a
`(1,1,32,128,128)` sample input, reference logits, and a model card.

```console
python scripts/build_bioimageio_package.py \
    --weights ./numorph_fold1_weights.pt --out ./bioimageio_pkg --fold 1 --repo .
python scripts/verify_package.py --package ./bioimageio_pkg
```

`verify_package.py` reloads the package the way a consumer would — imports the *packaged*
architecture file, loads the state dict strictly, regenerates the output from the packaged
input, and requires a 30-voxel axis to fail so the multiple-of-4 constraint is enforced
rather than merely documented.

The authoritative check is `bioimageio test`. On the shipped zip:

```
OVERALL: passed
  format validation (spec 0.5.12)
  reproduce test outputs from test inputs
  inference for legal sizes n: 0, 1, 2
```

Two packaging defects were found and fixed on the way, both worth knowing if you build
your own:

- `sample_tensor` **must be TIFF**. `imageio` has no `.npy` backend and fails with
  `Could not find a backend to open '<bytes>'`.
- the model `description` is **capped at 128 characters**; longer values fail validation.

Toolchain constraint: `bioimageio.spec` 0.5.12 needs `pydantic>=2.10.3` but breaks on
2.14 (`TypeError: 'index_key' is expected to be an integer or a string`), and numpy 2.x
with torch fails with a misleading `Numpy is not available`. Pinning numpy 1.26 with
torch 2.x is the working combination.

**Status: one model packaged (fold 1); citation placeholder still to replace.** The other
four folds are cross-validation replicates of the same recipe and are not packaged.

## How to run the smoke test

The command below runs the requested test workflow end-to-end:

1. Generates a random 3D input volume.
2. Initializes an untrained model.
3. Runs one forward pass.
4. Writes the segmentation mask as OME-TIFF.

```console
nuxnet-pred smoke-test --input-shape 8,16,16 --arch unet3d --classes 3 --in-channels 1 --output ./predictions/smoke_mask --no-cuda
```

This creates:

```text
./predictions/smoke_mask.ome.tiff
```

The smoke test exercises shape handling and I/O only — the weights are random, so the mask
is noise. Use the bundled example to judge accuracy.

You can inspect command help at any time:

```console
nuxnet-pred --help
nuxnet-pred predict --help
nuxnet-pred smoke-test --help
```

## Troubleshooting

**`Expected OME-TIFF axes to include ZYX, got axes 'QYX'`**
A plain TIFF. Write it with OME `ZYX` axes and `PhysicalSize` (see
[Preparing your own input](#preparing-your-own-input)).

**`input carries no PhysicalSize metadata`**
The file declares axes but no calibration. The run proceeds at the stored sampling and is
out of distribution. Add `PhysicalSizeZ/Y/X`.

**Tensor size mismatch inside the decoder**
Some spatial axis is not a multiple of 4. In training-grid mode the CLI pads tiles itself;
on the legacy path, or when calling the model directly, pad to a multiple of 4.

**Mask looks right but instances are wrong**
Instance extraction is a fixed-radius KDTree graph, not a trained segmenter. Tune
`--neighbor-radius` (default `2.0`), or cluster the mask with your own algorithm. The
mask is the model's output; the TSV is post-processing.

**Dice far below the round-trip ceiling**
Use `scripts/score_example.py` on the bundled pair first to confirm the install, then
compare your volume's ceiling. A large gap means the model is losing something; a small
gap means the resampling is.

**`strict=True` load fails with `Missing key(s)` / `Unexpected key(s)`**
The checkpoint is not from `nuxnet-training`, or the architecture has drifted from the
vendored file. `pytest tests/test_training_parity.py` will say which.

## Reproducibility notes

- `--seed` controls RNG seeding for Python, NumPy, and Torch.
- `--deterministic` controls runtime algorithm selection and backend settings to maximize deterministic behavior where supported.
- Deterministic mode can be slower (`cudnn.benchmark=False`) and can raise runtime errors if an operation has no deterministic implementation in the current stack.
- Full reproducibility is strongest when software/hardware versions are fixed (PyTorch/CUDA/cuDNN/driver/GPU model).
